# Translations: how they work

Ten languages: English plus Hindi, Marathi, Telugu, Tamil, Kannada, Malayalam, Bengali, Odia,
Gujarati. Anything missing falls back to English, always. A missing file, an unknown language or a
key nobody has translated shows English rather than failing.

## Where the copy lives

| Copy | Source | Translated by |
|---|---|---|
| PWA and family PWA screens | `apps/*/src/i18n/locales/<code>.json` | i18next in the browser |
| API copy — errors, pushes, nudges, reports, family | English in the code, via `copy()`; translations in `apps/api/src/i18n/locales/<code>.json` | the API, per request |
| Library articles | `apps/api/src/data/library.json`, overlaid by `library.<code>.json` | the API, per request |
| Corrections to any API string | the `Translation` table | the API, per request |
| Specialist profiles | the `Specialist` table, translated against the seeded English | the API, per request |

English is written in the code, not in a file. `copy()`, `copyList()`, `text()` and `plural()`
register their English literals at import, and `pnpm --filter @anuva/api i18n:extract` writes them
to `en.json` for translators. Edit the English in the code, then re-run extract.

## Which language a response is in

`Accept-Language` on the request, resolved by q-value, defaulting to English. Both PWAs send the
language the user picked. The response carries `Content-Language` and `Vary: Accept-Language`.

Pushes and jobs are different: they use the *recipient's* stored `preferredLanguage`
(`User` / `FamilyMember`), because the request that triggers a push is often someone else's — a
doctor's, or no request at all. `withLanguage(code, fn)` runs a block in a given language.

## The Translation table

Rows override the same key in the JSON bundle, so wording can be corrected from the admin panel
(Content → Translations) without a deploy. `key` is the dotted path, e.g.
`nudges.items.L1-001.options.0`.

Precedence: **table → bundle file → English → the English written in the code.**

The whole table is loaded into memory at boot and refreshed every 60s (`I18N_REFRESH_MS`), and the
refresh only reloads when the table has actually changed. Nothing queries the database per request.
If the table cannot be read — no migration yet, database down — the API logs a warning and serves
the files.

```bash
pnpm --filter @anuva/api i18n:extract                  # code → en.json (after any English edit)
pnpm --filter @anuva/api i18n:seed                     # files → table (only keys not in it)
pnpm --filter @anuva/api i18n:seed -- --language hi --force   # overwrite existing rows too
pnpm --filter @anuva/api i18n:export                   # table → files, to commit admin edits
pnpm check:i18n                                        # every bundle against English
```

Seeding never overwrites an existing row unless you pass `--force`, because a row that differs from
the file is usually somebody's correction. Run `i18n:export` first to get those corrections into
the files, commit them, then seed.

## Adding a language's translations

1. Run the prompts: `docs/I18N_SERVER_TRANSLATION_PROMPT.md` (API) and
   `docs/I18N_TRANSLATION_PROMPT.md` plus `docs/i18n-delta/PROMPT.md` (apps).
2. `pnpm check:i18n` — no missing keys, no dropped placeholders.
3. `pnpm --filter @anuva/api i18n:seed` so the admin panel can edit them.

## Tooling (`scripts/i18n/`)

```bash
node scripts/i18n/verify-api-bundle.mjs hi                 # one API bundle vs English: keys,
                                                           # placeholders, empties, duplicate options
node scripts/i18n/merge-app-delta.mjs pwa hi delta.json    # add strings to an app bundle safely
node scripts/i18n/library.mjs split                        # library.json → .i18n-work/lib-en/
node scripts/i18n/library.mjs status hi                    # which articles are still to do
node scripts/i18n/library.mjs verify hi                    # structure check, per article
node scripts/i18n/library.mjs merge hi                     # → apps/api/src/data/library.hi.json
```

**Never merge into an app bundle with a plain JSON parse and stringify.** JavaScript sorts
integer-like keys ascending whatever order they were written in, and the mood and sleep scales are
objects keyed 5 → 1 that render in key order, so a naive round trip flips them upside down without
any error. `merge-app-delta.mjs` exists to prevent exactly that.

Translation work in progress lives in `.i18n-work/` (git-ignored), one file per article, so an
interrupted run resumes from `library.mjs status` rather than starting over. `library.mjs merge`
refuses to write a language that fails `verify`, because one malformed article would put that
language's whole library back to English.

`apps/api/tests/i18n-bundles.test.ts` runs against every shipped bundle: keys, placeholders, no
empty strings, the Track page actually translated, and every translated check-in answer mapping
back to the exact English option that gets stored and scored.

## Finding copy that never gets translated

Start the API with `I18N_PSEUDO=1`. Every localised string comes back wrapped in `⟪…⟫`, so any
English on screen *without* brackets is text that no translation will ever reach. Diagnostic only —
never set it in production.

## Rules that the code depends on

- **Stored values stay English.** A tapped nudge answer goes through `canonicalAnswer()` and is
  saved as its English option; the weekly report and the tone classifier match on those strings.
  Band names (`Restful`, `Good`) are English internally and localised only at the edge.
- **Translated option lists keep their order and length.** Answers map back by position.
- **`id` fields are never translated**, in any `copy()` table.
- Caches that hold copy are keyed by language; ANU's semantic cache is English-only.

## Known limits

- The 14-day report **PDF** is always English: its built-in fonts have no Indic glyphs. The in-app
  and HTML versions are translated.
- ANU's **red-flag patterns are English-only**, so an emergency described in another language is
  caught by the model but not by the rules. Needs clinical review before non-English chat ships.
- Doctor-written notes, document titles and Q&A answers are shown as written.
- The doctor portal and admin panel are English.
